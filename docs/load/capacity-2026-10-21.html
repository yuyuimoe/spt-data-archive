How much load the archive holds

Measured on 21 October 2026 against the stack of compose.yaml: Caddy, the Api, PostgreSQL and Redis, each in its own container limited to 4 vCPU and 2 GB, with the generator next to them under the same limit. Repository commit 272f330 plus the proxy of ADR-0039.

The Api did not reach its limit.

6 000 clients — one request per second each, so 5 999 answers per second of 53 KB — pass with p95 8.1 ms and p99 15.7 ms, against a budget of 500 ms and 1 000 ms. That is 2% of the p95 budget. The Api held 2.7 of its 4 cores and PostgreSQL 0.9.

The Api would meet its 4 cores near 8 900 clients if the cost per answer stayed flat, so it used about 67% of that budget at the last proven point. Above 6 000 the load generator is what breaks, not the server: at 6 500 clients k6 was killed by its own 2 GB limit, and at 8 000 it answered only 2 325 of 8 000 requests per second. The last proven point is 6 000 clients; the limit of the deployment is above it and this rig cannot reach it.

  • The cache is the reason this works. 80% of the requests are ten pages that Redis answers in 7.4 ms; the other 20% run one SQL statement and cost 10.1 ms. Without the cache every request would be a miss, and the database would need 5 times the work it does now.
  • Compression costs CPU to save bandwidth. A page of 116 KB leaves as 109 KB with gzip or 59 KB with brotli: 4.7 times and 8.7 times smaller. The Api pays that with its own cores, and it is the largest single item in the Api's CPU.
  • PostgreSQL is not the bottleneck. One statement holds 93% of the database time and still takes 1.4 ms at its mean. Capping the work with the cache is what keeps it there.
  • The proxy is not free. Caddy spends 1.7 of its 4 cores of its 4 cores, and most of that is TLS and the JSON access log, which writes one line per request. A deployment that samples that log gives the proxy a good part of its budget back.

The pool of connections

The question was whether 30 connections is the right size for PostgreSQL with 4 cores. Measured at 4 000 clients, the three sizes behave the same, and PostgreSQL never had more than 4 connections busy: the pool was never the constraint, and the extra connections only sat idle holding a backend each.

The default of the Api is now 16: 34 of the 50 connections of compose.yaml stay free for the Archiver, migrations and an administrator, and two Api instances still fit under the same ceiling. The four timeouts of the pool came from the same checklist: a request waits 5 s for a connection, an idle connection closes after 60 s, and no connection lives longer than 30 minutes.

The ceiling of the rig

Two different things fail above 6 000 clients, and neither is the Api.

1. The generator runs out of memory

At 6 500 clients the k6 container was killed by its own 2 GB limit (exit 137). A virtual user holds one request in flight, so a run needs about rate × latency of them, and each one costs most of a megabyte once the answer is 53 KB of JSON that the client inflates.

2. A collapse poisons the next run

When the generator loses the schedule, the proxy keeps the unfinished answers of a slow client in memory and opens more connections to the Api. In that state Caddy reached 1.3 GB and started to answer 502 with cannot assign requested address: it had exhausted its own range of source ports. Every run in this report therefore starts from a clean stack, and a series is measured in one ascending pass.

How this was measured

  • The stack is tests/load/stack/compose.yaml: the four containers of compose.yaml and the generator, each with 4 vCPU and 2 GB. The data is a dump of the development archive: 4.0.13 and 4.1.6 official, and the five mod datasets.
  • One "client" is one request per second. 80% of the requests are ten popular pages, warmed before the run, so they are cache hits; 20% are pages nobody asked for yet, so every one of them runs SQL. Every cold request carries a unique tag in the query, which is what makes the cache key unique.
  • A run passes when p95 ≤ 500 ms, p99 ≤ 1 000 ms and fewer than 1% of the requests fail. Each run lasts 40 s after a warm-up, and the generator rises in steps of 500 clients; a binary search narrows the interval between the last pass and the first fail.
  • While a run happens, the driver samples the CPU and the memory of every container every 2 s, the connections of the read-only role in PostgreSQL every second, and resets pg_stat_statements before each run so the statements belong to that run alone.
  • Reproduce it with tests/load/scripts/stack.sh up and tests/load/scripts/search.sh all; tests/load/README.md holds the details. This page is rebuilt by python3 tests/load/scripts/report.py.
