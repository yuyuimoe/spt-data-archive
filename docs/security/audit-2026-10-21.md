# Security audit of the Api, 2026-10-21

Scope: the public surface of SPT Data Archive as it stands at commit `c95964f` plus the uncommitted cache
work in `src/SptArchive.Api/Caching`. That surface is `SptArchive.Api`: one read-only GraphQL endpoint over
PostgreSQL, with a Redis response cache in front of it.

The Archiver, the exporter and the mod runner are out of scope. They face the database and the file
system, not the internet.

## Method

This is a static review of the code and the deployment files, followed by read-only probes against the Api
that was running on `http://127.0.0.1:5099` (role `archive_reader`). No exploit was run, no data was
written and no fuzzing was done.

Checklists and references applied:

- `security-audit` skill (Netresearch DTT, v2.11.8): OWASP Top 10 2021, OWASP API Security Top 10,
  `api-security.md`, `input-validation.md`, `security-headers.md`, `error-message-sanitization.md`,
  `supply-chain-security.md`.
- `fullstack-code-audit-skill`, .NET part: `DOTNET_AUDIT_EXECUTION_STANDARD.md` (two-phase
  determination), `SEVERITY_RATING.md`, `DOTNET_SINK_REFERENCE.md`, and the `dotnet-graphql-audit`,
  `dotnet-aspnet-core-audit` and `dotnet-config-audit` skills.

Every finding below states its evidence, its impact and a concrete fix. A finding that was only possible
to judge from code is marked *static*. A finding that a live probe confirmed is marked *probe*.

Severity uses CVSS v3.1 base score.

## Status after the audit

The driver ordered the four findings with a real denial-of-service path, and ADR-0038 fixed them on
2026-10-21:

| Finding | State | Evidence |
|---------|-------|----------|
| F-01 | Fixed for one Api instance | A token bucket per client address, 100 answers and 17 refusals out of 120 requests in a burst, `429` with `Retry-After` and `RATE_LIMITED`. `/healthz` answered `200` throughout. The shared limit stays with the edge proxy (TD-05). |
| F-02 | Fixed | Brotli and gzip, outside the cache. A 513,918-byte page left as 109,320 bytes with gzip and 58,950 bytes with brotli. |
| F-03 | Fixed | `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `X-Frame-Options: DENY` on every answer, a refusal included. `HSTS` still belongs where TLS ends. |
| F-06 | Fixed | `Cache:MaxResponseBytes` (2 MB). A larger answer is answered and not stored. |
| F-04, F-05 | Open on purpose | Both must change in the change that adds authentication, and nothing else. |
| F-08 | Open | TD-55. A jsonb comparison still fails for a JSON scalar. |
| TD-53 | Fixed | The Api asks for at most 30 connections: 60 concurrent queries all answered `200` and the role never held more than 30. |

The tests that hold this are `tests/SptArchive.Tests/EdgeTests.cs`: they start the Api in the test process,
so they check the pipeline that the deployment runs.

### F-01: No rate limit at the Api, and one request may return 1.1 MB (Medium)

*Probe.* The Api has no rate limiter of its own (`Program.cs` has none), and the edge proxy is still only
planned (TD-05). One query returns a large answer for very little cost:

```
POST /graphql  { quests(sptVersion: "4.1.6", first: 200) { nodes { id data } } }
-> 200 OK, 1,155,389 bytes, 87 ms
```

A page of 200 items with every field is 518 KB. The cost limit counts fields and objects, not bytes, so a
legal query may return about 1 MB. Two hundred such requests at once moved about 220 MB and held the whole
database pool (TD-53).

Impact: a single client can saturate the 50-connection pool, the network link and the Redis memory with
ordinary, legal queries. This is a denial of service by volume, not by a bug.

Fix: put a rate limiter in front (Cloudflare, Traefik) and a per-IP token bucket in the Api
(`AddRateLimiter`), and treat response bytes as part of the cost. Until then, do not expose the container
port directly.

### F-02: Responses are never compressed (Low)

*Probe.* A request with `Accept-Encoding: gzip, br` gets the answer with `Transfer-Encoding: chunked` and
no `Content-Encoding`. JSON of this shape compresses about ten times.

Impact: ten times the bandwidth and ten times the time on a slow link, for bytes that the server already
produced. It multiplies F-01.

Fix: add `AddResponseCompression` with gzip and brotli, and call `UseResponseCompression` **inside** the
cache middleware (after `UseMiddleware<QueryCacheMiddleware>()`), so that the cache keeps storing the
uncompressed answer once and each client receives it compressed to what it asked for. Order matters: a
compression middleware placed before the cache would store one client's compressed bytes in a shared
entry. TD-54 tracks this.

### F-03: No security headers on the answer (Low)

*Probe.* An answer carries `Content-Type`, `Date`, `Server: Kestrel` and `X-Cache`, and nothing else. There
is no `X-Content-Type-Options: nosniff`, no `X-Frame-Options`, no `Referrer-Policy`, no `HSTS` and no
`Content-Security-Policy`.

Impact: small, because the endpoint answers JSON and no browser renders it as a document. A browser that
sniffs a JSON body as HTML is the case that `nosniff` closes. `HSTS` belongs at the TLS edge, which the
deployment does not have yet.

Fix: add `nosniff` and `Referrer-Policy: no-referrer` in the pipeline, and set `HSTS` where TLS ends.

### F-04: CORS allows every origin (Low)

*Static.* `Program.cs:27` uses `AllowAnyOrigin().WithMethods("GET", "POST").AllowAnyHeader()`.

Impact: this is correct for a public, anonymous, read-only API, and it is not a vulnerability today,
because the Api reads no cookie and no authorization header, so there is no ambient authority to abuse.
The risk starts the day authentication arrives: a browser would then send credentials from another site.

Fix: keep it, and make it a rule that authentication and `AllowAnyOrigin` never ship together. ADR-0008
and ADR-0037 already say the cache must change at that moment; CORS must change with it.

### F-05: Idempotency keys are a global namespace without an owner (Low)

*Static, with a probe.* A client sends `Idempotency-Key`. The Api stores the answer under
`gql:{version}:idem:{key}` for 300 seconds. Nothing ties the key to a client. Two consequences:

1. A client that loses its answer can replay it, which is the purpose.
2. Any client that knows a key can occupy it, or can fill Redis with 300-second entries that it names.

*Probe.* A replay of the same body answers from the store with `Idempotency-Replayed: true`. A key reused
for another body answers `409 IDEMPOTENCY_KEY_REUSED`. A key of 5 characters answers `400
IDEMPOTENCY_KEY_INVALID`.

Why the risk is bounded: the key is 8 to 128 characters from a fixed alphabet, so it cannot inject into
the Redis namespace; the entry lives 300 seconds; Redis is capped at 128 MB with LRU eviction; and every
byte stored is public data that any client may query anyway. A client can already fill Redis with ordinary
queries.

Fix: when authentication arrives, put the user or the token subject into the key, so one client cannot
occupy another client's key. Note it in the `Idempotency-Key` contract (ADR-0037, action item 3).

### F-06: The cache holds every answer in memory before it answers (Low)

*Static.* `QueryCacheMiddleware.ExecuteAsync` swaps `Response.Body` for a `MemoryStream` and answers from
`QueryAnswer.Bytes` after the query finishes. Every cacheable request therefore holds its whole answer in
managed memory, and a legal answer is up to 1.1 MB.

Impact: about 1 MB of extra memory per concurrent cacheable request, for the time of one query. With the
pool at 50 connections that is about 55 MB, which the Api holds today. It grows if the pool or the answer
size grows.

Fix: cache only answers below a ceiling (`Cache__MaxResponseBytes`, for example 2 MB) and stream the rest
to the client as they arrive. TD-54 mentions this with the compression work.

### F-07: `X-Cache` and `Idempotency-Replayed` tell the client about the inside (Info)

*Probe.* The answer states whether it came from Redis (`MISS`, `HIT`, `SHARED`) and whether it is a replay.
This is deliberate: it makes the cache testable and observable. It tells an attacker when a cache is warm
or cold, which is worth little against a 60-second lifetime.

Fix: none. Keep it, and keep the header out of any future response that is not public.

### F-08: A jsonb column compared with a JSON scalar is an internal error (Low)

*Probe.* A filter on a jsonb column accepts an `Any` value, and `Any` accepts a JSON string, a number, a
boolean and null. Compared with a string, the query fails inside PostgreSQL:

```
POST /graphql  { items(where: { props: { eq: "x" } }, first: 1) { nodes { id } } }
-> 200 OK  {"errors":[{"message":"Unexpected Execution Error","path":["items"]}],"data":{"items":null}}
```

The log states the cause: `22P02: invalid input syntax for type json`, "JSON data, line 1: x". The value
reaches the jsonb parameter without the quotes that make it JSON, so Postgres refuses it. A JSON object or
array works (`props eq {}` answers an empty list). A filter for `props.eq` therefore works for one shape of
value and fails for the others.

Impact: a client that filters a document by a scalar gets an answer that names no cause, and every such
request raises a server-side exception and a log entry. It is not a leak: the message the client sees is
the generic one, and the detail stays in the log. It is a log-amplification path and a broken contract.
TD-55 tracks it.

Fix: make the `Any` -> jsonb comparison write valid JSON for every value (quote a string, write a number,
a boolean and null as they are), and add a test per value kind. Until then, keep the client contract to
objects and arrays, and say so in the schema description.

## Checked and clean

These were checked and found sound.

- **No write path.** The schema has no `Mutation`. A `mutation` request answers `400`, "This GraphQL schema
  does not support `Mutation` operations". The Api connects as `archive_reader`, a role with `SELECT` and
  nothing else (`docker/initdb/01-reader-role.sh`); a `DELETE` from that role is refused (measured on
  2026-10-20 during the backup test).
- **No SQL injection surface.** Every resolver is LINQ over `IQueryable`. The `side` argument of
  `customizations` compiles to a parameterized array containment check. No string reaches SQL.
- **Depth and cost.** Depth 10, body 1 MB, 10-second timeout, cost 20,000 fields and 2,000 objects. Probes:
  12 aliased pages of 200 rows answer `HC0047` with `typeCost 2413`; `first: 100000` answers `HC0047` with
  `typeCost 100002`; a 40 KB body answers `400`.
- **No batching bypass.** An array of two operations answers `400 HC0009 Invalid GraphQL Request`, so the
  cost limit cannot be multiplied by packing many operations into one body.
- **Introspection is not an amplifier.** The whole schema is 28,759 bytes and answers in 4 ms. It stays on,
  because schema discovery is the product.
- **jsonb text operators are gone.** `JsonFilter.cs` offers `eq` and `neq` only on `Any` fields, so the
  Postgres error path that once answered "Unexpected Execution Error" is not reachable from the schema.
- **No stack trace or internal path reaches a client.** An unhandled exception answers "Unexpected
  Execution Error" with no code, no path and no detail; the detail goes to the console log only (probed with
  F-08). Postgres redacts the detail of its own errors, because the connection string does not ask for it.
  Serilog writes to the console, at Information, with Microsoft at Warning.
- **Cache keys cannot collide.** A plain key is `gql:{version}:{64 hex}`, an idempotent key is
  `gql:{version}:idem:{key}`, and the alphabet of a key cannot produce 64 hex characters after `idem:`. An
  entry also states the SHA-256 of the body that produced it (the `SARC1` frame), so a key cannot answer a
  body it did not produce — probed: `409 IDEMPOTENCY_KEY_REUSED`.
- **One cold answer costs one query.** Probed with k6: 200 clients that miss the same answer together ran
  one query (`1 miss, 119 shared, 80 hit`); the same test with `Cache__MaxFlights=0` ran 200 queries. The
  flight map is bounded and a failed flight is never shared.
- **The cache is not a dependency.** A cache that fails is skipped for 30 seconds and the request answers
  from PostgreSQL (probed on 2026-10-21: one slow request, then 55 ms answers).
- **Secrets.** `.env` is ignored, `.env.example` holds empty values, both compose files demand the two
  passwords (`${...:?set ...}`) so a missing secret stops the stack instead of defaulting. `git grep` over
  the tracked files finds no credential. The development passwords in `docker/compose.yml` are documented
  as development-only, on loopback.
- **Published ports.** `compose.yaml` publishes only the Api. Postgres and Redis are reachable on the
  compose network only. Redis has no password and no TLS, which is acceptable while it is not published,
  and must change if it ever is.
- **Container user.** Both Dockerfiles end with `USER $APP_UID`, so the process is not root.
- **Dependencies.** Versions are pinned centrally in `Directory.Packages.props` with transitive pinning on.
  `dotnet list SptArchive.slnx package --vulnerable --include-transitive` against nuget.org reported no
  vulnerable package for any of the four projects (2026-10-21).
- **Errors are cheap to log and cheap to answer.** No request body is logged, so no query or variable
  reaches the log at the default level.

## Out of scope

- The Archiver, the exporter, the mod runner and the canonical comparison.
- The data itself, and whether it is correct.
- The Gherkin specs and the test suite.
- TLS, DNS, the firewall and the reverse proxy, none of which exist in this repository.

## Limits of this audit

- Static review plus read-only probes. No exploit was developed, no scanner was run over the source, and
  no fuzzing was done.
- Dependency checking is limited to `dotnet list package --vulnerable` against nuget.org. No container
  image scan (`trivy`) was run.
- The probes ran against the development database on loopback, without TLS and without an edge proxy, so
  the network position of the real deployment was not reproduced.
- The two load points in F-01 come from a loopback measurement; a real link would be slower, which makes
  the amplification worse and not better.

## Recommended order of work

1. **F-01**, with TD-05: a rate limiter at the edge and in the Api. It is the only finding with a real
   denial-of-service path.
2. **F-02** and **F-06**, together in TD-54: compression and a response-size ceiling.
3. **TD-53**: cap the reader pool, so a burst waits instead of failing.
4. **F-03**: two headers, one line.
5. **F-08** with TD-55: a comparison must accept every JSON value that the schema announces.
6. **F-04** and **F-05**: do them in the change that adds authentication, not before.
